## Idioma do projeto

O português (pt-BR) é o idioma padrão deste projeto: documentação, comentários no código, mensagens de commit e comunicação com o usuário devem ser em português. Textos técnicos que não têm tradução natural (nomes de bibliotecas, comandos, flags, termos como "MVP" ou "stack") permanecem em inglês onde for o padrão do ecossistema.

## Status

Portal FinQuant — um portal educacional em Django sobre finanças quantitativas para leigos, construído como MVP de TCC. Já está montado com página inicial, artigos, um simulador de juros compostos, cadastro/login de usuário e um formulário de avaliação do site. Veja o `README.md` para instruções de instalação e deploy.

## Comandos

Todos os comandos assumem o ambiente virtual ativado: `source venv/Scripts/activate` (Git Bash) ou `venv\Scripts\activate.bat` (cmd).

- **Rodar o servidor de desenvolvimento:** `python manage.py runserver`
- **Aplicar migrações:** `python manage.py migrate`
- **Criar uma migração após alterar modelos:** `python manage.py makemigrations`
- **Criar um usuário administrador:** `python manage.py createsuperuser`
- **Verificação do sistema (detecta erros de configuração sem subir o servidor):** `python manage.py check`
- **Coletar arquivos estáticos para deploy:** `python manage.py collectstatic --noinput`
- **Shell do Django:** `python manage.py shell`
- Ainda não existe suíte de testes automatizada para o projeto todo (a maioria dos apps tem um `tests.py` vazio, gerado pelo `startapp`); não há test runner configurado além do padrão do Django (`python manage.py test`). O app `simuladores` é a exceção — veja "Padrão dos simuladores" abaixo.

## Arquitetura

Projeto Django monolítico (`config/`) com um app por funcionalidade do MVP, seguindo as convenções padrão do Django (models/views/urls/admin por app, sem camada de API separada — apenas templates renderizados no servidor):

- `core/` — página inicial, busca os 3 artigos mais recentes do app `conteudo`. Também cuida de busca e prévia de link (desde 09/11/2026): `core/seo.py` tem o título e a descrição de cada rota, que o context processor `seo` entrega ao `base.html` (meta description, canonical, Open Graph). Página nova: acrescente a rota em `PAGINAS`. Ainda no `core`: `robots.txt` (bloqueia robôs em `/estudo-caso/analise/`, que dispara cálculo pesado), `sitemap.xml` (`core/sitemaps.py`) e `/favicon.ico`. As imagens da marca em `static/img/` (favicon, ícone da Apple, `previa.png` de 1200x630) saem de `scripts/gerar_imagens_marca.py`.
- `contas/` — cadastro (`CreateView` + `UserCreationForm`), login/logout (views nativas de `auth` do Django). Usa o modelo padrão `auth.User`, sem customização. **Limite de login (desde 09/11/2026):** 5 senhas erradas para o mesmo usuário o bloqueiam por 15 minutos, na tela de Entrar e no `/admin/` (`contas/limite_login.py`, backend `BackendComLimite`). O contador fica no cache em memória, o que só vale com um processo do gunicorn: se subir `--workers`, o cache precisa ser compartilhado. **Recuperação de senha (desde 09/11/2026):** o e-mail sai pela API HTTPS do Brevo (`django-anymail`, ativado pela `BREVO_API_KEY` no Render), porque o Render gratuito bloqueia as portas SMTP. A chave é restrita a e-mails transacionais e **expira em 10/11/2027 ou após 90 dias sem uso**: se o "esqueci a senha" parar de enviar (o log do Render mostra "Failed to send password reset email"), gere outra chave no Brevo e troque no Render. Conta de login social sem senha local não recebe o e-mail, de propósito.
- `conteudo/` — modelo `Artigo` (título, slug, resumo, corpo, categoria) + registro no Django Admin para gestão de conteúdo (sem CMS customizado). Views de listagem e detalhe.
- `simuladores/` — juros compostos, dívida no rotativo do cartão e calculadora de meta financeira, mais uma página-índice em `simuladores:index`. Cálculo puro em `simuladores/views.py`, sem modelo persistido; o resultado é calculado a cada envio do formulário e renderizado na mesma página. Veja "Padrão dos simuladores" abaixo antes de adicionar um novo.
- `avaliacoes/` — modelo `Avaliacao` (nota de 1 a 5 + comentário, com FK opcional para o usuário) que registra o feedback dos usuários sobre o site; esses dados alimentam a análise de qualidade na entrega final do TCC.
- `templates/base.html` — layout compartilhado (navbar, Bootstrap 5 via CDN, mensagens) que os templates de todos os apps estendem.
- `static/css/site.css` — sistema de design do portal (tokens de cor/tipografia, remapeamento das variáveis do Bootstrap). Veja "Identidade visual" abaixo.

As configurações (`config/settings.py`) são lidas de variáveis de ambiente via `django-environ`, a partir de um `.env` local (ignorado pelo git; veja o modelo em `.env.example`). O banco é SQLite, a menos que `DATABASE_URL` esteja definida (produção/Render usa PostgreSQL). Arquivos estáticos são servidos via Whitenoise em produção.

- `estudo_caso/` — "Análise de ações" (`/estudo-caso/`): uma regra de médias móveis em ações do Ibovespa, comparada com a Selic, comprar e segurar e o Ibovespa, com testes estatísticos. Veja "Análise de ações" abaixo.

## Análise de ações (`estudo_caso`)

Veio do projeto `Script Analise Quantitativa` (pasta irmã), que era um app Streamlit. **Desde 09/11/2026 a cópia oficial do núcleo é a do portal** (`estudo_caso/quant/`); a pasta do Script ficou como versão Streamlit de referência. Mudanças no cálculo são feitas aqui.

- `quant/` — o núcleo, Python puro (pandas/numpy/scipy, sem Django). Entrada única: `servico.executar(config) -> dict` JSON. Testes em `quant_tests/`, com `pytest estudo_caso/quant_tests` (precisa do `requirements-dev.txt`); não são achados pelo `manage.py test` de propósito (pasta sem `__init__.py`).
- `apresentacao/` — textos da página (`textos.py`), formatação brasileira, gráficos Plotly e o resumo em PDF (reportlab, com a fonte DejaVu de `fontes/` no Linux). Para mudar um texto, edite `textos.py` ou `quant/leitura.py`.
- `telas.py` — as funções `tela_*`, vindas do `app_streamlit.py`. O objeto `st` é um imitador (`_Pagina`) que escreve HTML. Não reescreva as telas em templates: os textos são os mesmos que foram revisados. **Desde 09/11/2026 a organização é própria do portal (pedido do autor):** cada tela tem uma introdução curta no alto (números-chave, alerta ou parágrafo) e o resto em abas com `um_por_vez`, no modelo de "A divisão do dinheiro". No máximo dois níveis de abas. Os textos de custo e capital fixos (`tx.CUSTOS_FIXOS`, `tx.CAPITAL_FIXO`) ficam nas abas "As operações › Custos e imposto" e "Quanto o dinheiro teria virado › As alternativas", não no passo 1.
- `execucao.py` — a análise roda numa thread (uma por vez) e o resultado vai compactado para o cache `analises` (tabela `estudo_caso_cache` no banco). A chave junta a versão do núcleo, a configuração e a data do último pregão nos CSVs.
- `dados/` — CSVs de preços, Ibovespa e Selic, versionados no git. As requisições nunca baixam nada. `manage.py atualizar_dados_estudo` atualiza (roda no build do Render, disparado toda semana por `.github/workflows/atualizar-dados.yml`); `manage.py precalcular_estudo` deixa prontas as configurações padrão.
- **Procedência dos dados (desde 09/11/2026):** a coleta descarta o pregão do próprio dia (baixado com a bolsa aberta, traria o preço do meio do pregão) e grava `dados/coleta.json` com a data e a hora da coleta e, por CSV, a fonte, o último dado e o hash SHA-256 (os CSVs são gravados com LF, para o hash bater com o do git). O `execucao._guardar` junta ao resultado a parte das séries usadas (`res["procedencia"]`), mostrada na aba "De onde vêm os dados". O Yahoo devolve os preços ajustados com diferenças na 7ª casa decimal a cada download: um download novo reescreve os CSVs inteiros, então não suba um download local para o git só para corrigir uma linha.

- **Custo e capital fixos (desde 09/11/2026, decisão do autor):** o passo 1 não pergunta mais o custo nem o capital. Vale sempre "Tarifas da B3 e imposto" e R$ 100.000 (`forms.CUSTO_FIXO`/`CAPITAL_FIXO`), explicados como premissas (`tx.CUSTOS_FIXOS`, `tx.CAPITAL_FIXO`). O núcleo continua aceitando os dois, porque o teste "Sensibilidade ao custo" usa `sem_custo` por dentro. Ao mudar um texto que fica guardado no resultado (como os de `quant/leitura.py`), suba `execucao.REVISAO_TEXTOS`, senão o cache continua servindo o texto antigo.
- **Pré-cálculo de madrugada (`execucao.precalcular_ocioso`):** uma thread iniciada no `apps.py` (só no gunicorn) calcula, dentro da janela `ESTUDO_JANELA` (horas de Brasília; padrão "2-5", vazio = desligado), o que falta no cache entre as 60 seleções automáticas e cada ação sozinha com os padrões. Ela cede a vez a quem pedir uma análise, parando na próxima troca de etapa. O deploy com os preços novos é no sábado à 01:00, logo antes da janela. Ela só começa `execucao.PAUSA_INICIAL` depois da subida: sem essa pausa, o primeiro teste (09/11/2026) deixou o site sem responder por ~10 min; com ela, a volta completa levou ~64 min com o site respondendo em menos de 1 s. O `estudo_caso/vigia.py` grava no log a pilha de todas as threads se uma requisição ficar presa (ou se o processo congelar): é por ali que se investiga um travamento.

Exceções deliberadas aos padrões do portal:
- **`float`, não `Decimal`:** o núcleo calcula com pandas/numpy; a apresentação formata em texto (`formatacao.py`).
- **GET, não POST:** as escolhas e a tela atual (`?tela=N`) ficam no link, que pode ser compartilhado.
- **Plotly, não SVG à mão:** os gráficos são os de `graficos_plotly.py`, desenhados pelo plotly.js do CDN (versão lida da biblioteca Python). No tema escuro, o `static/js/estudo_caso.js` troca as cores de fundo, texto e grade.
- **Thread em segundo plano:** no Render free, a seleção automática passa do limite de tempo de uma requisição. O gunicorn roda com 1 processo e 4 threads (`render.yaml`).

## Padrão dos simuladores

Este é o padrão a seguir ao criar um novo simulador em `simuladores/` (estabelecido pelos simuladores de juros compostos, dívida no cartão e meta financeira — use `DividaCartaoView`/`DividaCartaoForm`/`divida_cartao.html` como referência mais completa, por cobrir também o caso de alerta).

- **View**: `FormView` cujo `form_valid` **não redireciona** — chama `self.get_context_data(form=form)`, injeta `contexto['resultado'] = self._calcular(dados)` (um `@staticmethod`) e retorna `self.render_to_response(contexto)`, reexibindo a mesma página com o resultado.
- **Cálculo**: tudo em `Decimal` (nunca `float`, exceto ao converter valores para o gráfico — ver abaixo), iterando mês a mês. Se a simulação puder rodar por muitos meses com o saldo só crescendo (ex.: um cenário de "nunca quita"), use o decorador `_precisao_alta` de `simuladores/views.py` (precisão 220) — o contexto padrão de 28 dígitos estoura em juros compostos por 600 meses (15% ao mês já dava erro 500 até 09/11/2026). A precisão cobre o pior caso porque o `TaxaComPeriodoMixin` recusa taxa acima de 100% ao mês (`forms.TAXA_MENSAL_MAXIMA`).
- **Form**: `forms.Form` simples (não `ModelForm` — os simuladores não persistem nada), campos `DecimalField`/`IntegerField` com `widget=forms.NumberInput(attrs={'class': 'form-control', 'step': '0.01'})`. Se o simulador tem taxa de juros, herde de `TaxaComPeriodoMixin` e declare `periodo_taxa = campo_periodo_taxa()` logo depois de `taxa_mensal`: o usuário escolhe "ao mês" ou "ao ano" e o mixin entrega sempre a taxa mensal ao `_calcular`.
- **Rota**: uma entrada em `simuladores/urls.py` (ex.: `path('novo-simulador/', views.NovoSimuladorView.as_view(), name='novo_simulador')`), mais um card novo em `templates/simuladores/index.html` linkando para ela.
- **Template**: estende `base.html`, layout `col-md-5` (formulário) + `col-md-7` (resultado, com placeholder ilustrado quando `resultado` é `None`). O gráfico é um SVG desenhado à mão via JS vanilla (sem Chart.js), num arquivo só para todos os simuladores: `static/js/grafico.js` + `static/css/grafico.css`. No template, faça `{% load static %}`, carregue o CSS no `{% block extra_head %}` e o `<script src="{% static 'js/grafico.js' %}">` no fim do `{% block content %}` (depois do `<figure>`), copiando o `<figure class="... grafico-evolucao">` de `templates/simuladores/juros_compostos.html` (ids `pontos-grafico`, `grafico-evolucao-svg`, `grafico-evolucao-tooltip`). Os dados chegam via `{{ resultado.pontos_grafico|json_script:"pontos-grafico" }}` no formato `[{mes, saldo}, ...]` (saldo em `float`, não `Decimal`, pois é o único ponto onde o JS precisa do valor). Para simuladores de tom de alerta (dívida, por exemplo), some a classe `grafico-alerta` ao `<figure>` (troca a linha para `var(--fq-rust)`); para simuladores de "crescimento" mantenha a paleta azul padrão.
  - **Legibilidade do gráfico em qualquer tela (não mexa sem entender o porquê)**: em `static/js/grafico.js`, o `viewBox` do SVG **não** é fixo em `800x320` — o script mede o tamanho real renderizado (`svg.getBoundingClientRect()`) e ajusta o `viewBox` para bater com ele antes de desenhar. Isso faz o `font-size` dos rótulos (classe `.rotulo`, `13px`) corresponder a pixels de tela de verdade em qualquer largura de card, em vez de encolher proporcionalmente num card estreito de mobile (era assim antes, e o texto ficava ilegível a ~4px). Duas consequências que também precisam ser copiadas junto: (1) o número de marcações do eixo X é calculado a partir da largura disponível (`numTicksXDesejado`, com base na largura medida do rótulo mais largo via `medidor.measureText`) em vez de um `6` fixo, senão os rótulos "Mês N" se sobrepõem em telas estreitas; (2) o último rótulo do eixo X usa `text-anchor: end` (não `middle`) para não ser cortado na borda do `viewBox`, e o penúltimo rótulo é removido quando não sobra espaço entre os dois. Se criar um simulador com um eixo/rótulo diferente de "Mês N", reaproveite a mesma lógica de medição em vez de valores fixos.
- **Painel "Como calculamos isso?"**: **obrigatório em todo simulador**, um `<details>` colapsado abaixo da tabela de resultado, com (1) uma frase explicando o método em linguagem simples, (2) a fórmula usada (em `fq-numeros`), e (3) um exemplo numérico pequeno e completo que o usuário consiga conferir manualmente numa calculadora comum. Esse exemplo deve ser reaproveitado como caso de teste unitário de `_calcular` — serve tanto de documentação viva da fórmula quanto de verificação de precisão. Inclua também `{% include "simuladores/_conversao_taxa.html" %}` no painel e, no card de resultado, `{% include "simuladores/_premissas.html" with nota="..." %}` (valores nominais, sem inflação nem IR, e a taxa mensal equivalente quando a taxa veio ao ano).
- **Testes**: `simuladores/tests.py` cobre as funções `_calcular` diretamente (`TestCase`, sem precisar de `Client`/request), usando os exemplos do painel "Como calculamos isso?" como valores esperados, mais os casos-limite relevantes (taxa 0%, meta já atingida, dívida que nunca quita etc.).
- **Sem model/admin**: os simuladores são calculadoras stateless — não crie `models.py`/`admin.py` a menos que o simulador precise persistir algo (nenhum precisa até hoje).

## Identidade visual

Direção "painel institucional": neutra, sóbria, funcional — não editorial nem decorativa. Ao criar uma página nova, siga estas convenções em vez de estilizar do zero:

- **Tokens de cor/tipografia**: custom properties com prefixo `--fq-*` no `:root` de `static/css/site.css`, remapeadas nas variáveis nativas do Bootstrap 5.3 (`--bs-primary`, `--bs-body-bg`, `--bs-link-color`, variáveis locais de `.btn-*`/`.table-*`/`.dropdown-menu` etc.) — componentes prontos do Bootstrap herdam a paleta automaticamente, sem precisar de classes extras. Cores principais: `--fq-paper`/`--fq-paper-raised` (fundo/cards), `--fq-ink`/`--fq-ink-muted` (texto), `--fq-teal` (accent slate-azulado — botões, links, destaques), `--fq-gold` (verde-oliva, uso funcional tipo "positivo"), `--fq-rust` (terracota, "negativo"/alerta). Cada uma tem variante redefinida em `[data-bs-theme="dark"]`.
  - **Atenção**: `--fq-ink` e `--fq-paper` invertem de sentido entre os dois temas (ink vira claro no escuro, paper vira escuro). Para algo que precise ficar sempre escuro nos dois temas (ex.: a navbar, o cabeçalho da tabela do simulador), use os tokens fixos `--fq-nav-bg`/`--fq-nav-fg` (ou `--fq-teal`, que também é consistente), nunca `--fq-ink`/`--fq-paper`.
- **Tipografia**: Space Grotesk (títulos, `--fq-font-display`), IBM Plex Sans (corpo, `--fq-font-body`), IBM Plex Mono (números/dados, `--fq-font-mono` — usar a classe `.fq-numeros` em valores monetários/tabelas). Carregadas via Google Fonts no `<head>` do `base.html`.
- **Layout**: cantos quase retos (`--bs-border-radius*` reduzidos), cards sem sombra (só borda 1px em `--fq-rule`), rótulos de seção com a classe `.fq-eyebrow`, divisor de assinatura `.fq-regua` (régua com marcações) abaixo de títulos de seção.
- **Ilustrações**: SVGs de "painel de dados" (gráficos, crachás, medidores — nunca cenas decorativas/ilustrativas) em `templates/ilustracoes/*.svg`, incluídos com `{% include "ilustracoes/nome.svg" %}` (não `<img>`, para herdar `currentColor` e adaptar ao tema). Sempre com `width`/`height` explícitos no `<svg>` (evita ícone gigante antes do CSS carregar) além da classe `fq-ilustracao` (aplica cor e teto de tamanho responsivo).
- **Selos de categoria de artigo**: `templates/conteudo/_categoria_badge.html` — um ícone de linha por categoria; incluir com `{% include "conteudo/_categoria_badge.html" with categoria=artigo.categoria label=artigo.get_categoria_display %}`.
- Os `<link>`/`<script>` dos CSS e JS próprios terminam em `{{ versao_estatico }}` (context processor em `core/context_processors.py`): com `DEBUG` ligado vira `?v=<agora>` e qualquer edição aparece sem hard refresh; em produção fica vazio, porque o Whitenoise já põe o hash no nome do arquivo. Até 09/11/2026 era `?v={% now 'U' %}`, que obrigava o navegador a baixar o CSS de novo em toda página.
